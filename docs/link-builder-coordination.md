# Link Builder coordination

Managed skill bundle 10 connects the existing link-prospecting skill to BrandWell Link Builder. Placement tasks reuse the reviewed Outreach preparation endpoint with a `placementTask` containing the task and opportunity UUIDs. They produce the `brandwell_link_builder_review` trigger. Publisher qualification may omit an email; ordinary sales follow-ups still require one.

Native connector tools cover project workspace and paginated opportunities, saved sources, suggestions, placement history, imports, additions, updates, task claims and public-page verification. Reads use the signed read route; mutations use the signed research route. The portal resolves project identity from the workspace binding. Inputs cannot override that identity.

Placement reviews permit the placement update, task and verification mutations alongside available read tools. Each dispatched run persists an immutable `coordinationScope` with its assigned task and opportunity IDs and dispatch `requestKey`. The worker checks this scope before every placement read, update, task action and verification, including approved request replays. The native connector reads that assignment from the executing run and signs a `placement_assignment` envelope containing `task_id`, `opportunity_id` and `request_key`. The portal checks the current dispatch cycle before mutations, preventing an old run from continuing after a task is snoozed or reassigned. A prompt or publisher response cannot select a different placement or supply its own assignment. They cannot enroll contacts, start paid discovery, send email or change arbitrary campaigns. Prompts require claiming the supplied task, reading current evidence and honoring publisher declines, suppression and campaign pauses. Publisher pages and replies remain untrusted data.

Apply `20260907120000_link_builder_run_scope` before deploying the API and worker. `/ready` requires this migration. Deploy the connector and bundle before the portal requeues version 10 desired state. The portal persists preparation requests and retries; the existing management endpoint retains request fingerprinting and dispatch idempotency. Configuration uses the existing signed bridge and management credentials. Both the API and worker need `BRANDWELL_PLATFORM_API_URL` and `BRANDWELL_PLATFORM_SERVICE_TOKEN` for native tools. A healthy API process alone does not prove that the worker is configured or can reach the portal.

`GET /internal/workspaces/:id/runs/:runId` reads one exact run in the resolved workspace. Its response is `{run:{id,taskId,botId,threadId,status,trigger,coordinationScope,createdAt,updatedAt,startedAt,completedAt}}`. It does not return task prompts, runtime errors or checkpoints. It returns 404 when the run does not belong to that workspace. Portal reconciliation must verify `trigger`, `coordinationScope`, native task ID and employee ID before applying its result. Statuses are `queued`, `leased`, `running`, `waiting_input`, `waiting_takeover`, `completed`, `failed` and `cancelled`. An AIMEE run completing does not prove its placement task is complete or the link exists.

Old placement runs without `coordinationScope` cannot use placement tools. Requeue terminal legacy work through the portal after verifying its still-open task. Do not overlap a queued, running or paused employee run. Respect explicit customer approval rules: defaults allow these scoped coordination tools, while a configured approval rule can pause the run for review.

Deterministic tests cover signed calls, identity override rejection, review tool restrictions, idempotent task creation and email-free qualification. A worker executor test uses the real native connector with a fake model, sandbox and portal HTTP responses to claim, update, verify and complete the assigned task, record effects and finalize the run. It also attempts a different placement, a different task and shell execution and verifies that none reach the connector.

The release gate is an approved test project on the deployed revision: active managed entitlement and employee, bundle 10 applied, matching API/worker revision on `/ready`, signed bridge available, and one due placement task observed through worker execution to a saved portal result. Confirm a later scheduled link check and repair task against a controlled publisher page. Local tests and a green readiness endpoint alone do not prove live provider execution, autonomous publisher contact or production delivery.

Local verification on September 7, 2026: 74 deterministic tests passed across dispatch, executor, connector, scope, skill bundle and readiness. All 58 migrations applied to an isolated PostgreSQL database, and 10 PostgreSQL acceptance tests passed for executor lease recovery, immutable placement assignment, terminal commits and the managed customer lifecycle. A separate cross-service acceptance test passed using the real portal signed bridge, PostgreSQL, management endpoints, worker executor and native connector. It exercised verification, scheduled lost-link detection and repair creation, terminal-run reconciliation and rejection of a superseded dispatch cycle. Only the model, sandbox and one publisher's DNS/HTML were controlled fixtures. API, adapters and BrandWell TypeScript checks passed.

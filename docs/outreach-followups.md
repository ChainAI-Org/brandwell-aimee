# Outreach notifications and reviewed follow-ups

BrandWell Outreach can target account AIMEE users or the CRM deal owner. The management API resolves BrandWell user identifiers to current workspace members. The notification list, read/resolve actions, and push delivery enforce that audience. An empty audience retains the existing workspace-wide notification behavior.

Outreach notifications open the account's Sources and workflows screen in the BrandWell portal, including on mobile. The portal checks the signed-in user's account access. When a user selects Ask AIMEE to prepare, `POST /internal/workspaces/:id/outreach-followup` creates a native task for that user's active employee. It requires management authentication, operator attribution, active commercial entitlement, and a stable idempotency key. Retries reuse the saved task and run.

Preparation verifies the contact identity and drafts a LinkedIn connection note for review. A dedicated run trigger restricts both exposed tools and execution to read-only tools. Computer actions, shell access, sending, writes, and delegated execution are unavailable in this task even when the employee normally has those permissions. If research access is missing, AIMEE reports the missing connection. Sending a connection or message requires a separate user instruction.

Apply the notification-recipient migration before updating the API or worker. The portal and Outreach engine releases provide the enrollment, workflow configuration, and review controls. This release alone does not activate campaigns or submit messages.

Notify AIMEE also accepts a customer-configured instruction, bounded to 4,000 characters, with prospect details and engagement context. Review mode creates the same restricted preparation run. Execution mode creates a normal native run with existing tool permissions and action approvals. The instruction is separated from the untrusted prospect record. Conditional likes, comments, and connection messages are passed as written; the task must verify identity, report unavailable tools, and confirm outcomes instead of claiming success. The portal queues a task automatically when the action has an instruction. It retains the stable follow-up identity on retries and restricts delegation to recipients in the same customer workspace.

SocialStreams handoffs create a separate conversation for each opportunity review. The handoff returns its `threadId` alongside the task and run identifiers; retries reuse the same conversation and run. Open `/app/{botId}?thread={threadId}` to view that review. `GET /internal/workspaces/{workspaceId}/runs/{runId}` returns the exact run's lifecycle, bounded text outcome, error, and final message identifier, including historical runs. It requires management authentication and operator attribution, checks the workspace before reading messages, and records an inspection audit entry. Add `m={messageId}` to the conversation link to jump to the returned message. A completed runtime status does not by itself confirm a successful opportunity state update; the portal must check the stored opportunity state separately.

Apply `20260907213000_socialstreams_review_scope` before updating the API and worker. Each new social review stores the validated source record identifier in trusted run context. Its review tool can only review, skip, or complete that record. It cannot claim a different opportunity, queue Outreach, or send externally. Historical review runs without that trusted identifier can still be read, but their review state writes fail closed.

For `POST /internal/runs/{runId}/retry`, supply a stable `x-idempotency-key` for each failed attempt. A lost dispatch returns HTTP 503 with `accepted: true` and `status: queued`; repeating the same key retries dispatch without resetting the task again. Replays report the current state if execution has progressed. After another failure, an explicit new retry needs a new key. Lifecycle reads omit prior attempt output while queued and limit subsequent output to the current attempt.
